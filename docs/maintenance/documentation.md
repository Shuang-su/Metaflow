# 文档维护规范

## 写作语言

中文是唯一维护语言。API、命令、路径、字段、格式名和上游正式名称保留英文；不要为了“完整”创建同步英文副本。

## 选择文档类型

- 快速开始：让第一次使用者完成一条成功路径。
- 操作指南：解决一个明确任务，可以假设读者已有基础。
- 概念：解释边界、关系和决策。
- 参考：字段、参数、契约和稳定查表。
- 维护：开发、同步、发布、排障与治理。
- 历史入口：只负责分类和跳转，不把旧结论改写成当前事实。

不要把完整 API 表塞进教程，也不要把实施过程写进用户正文。结构决策和文件步骤属于 Spec/Plan。

## 事实来源

版本、上游、schema、导出和构建事实必须链接 [中文文档体系规范](../specs/chinese-documentation-system.md) 列出的机器来源。摘要可以重复当前值，但不能成为唯一记录。

版本变化时至少搜索：

```bash
rg -n '5\.18|1\.26\.2|2\.28\.0|schema `1\.2`' README.md docs metaflow-viewer/README.md
```

搜索结果不是自动替换清单；历史 ledger 中的旧版本应保留。

## 链接和导航

- 使用相对链接连接仓库文件；外部页面使用 HTTPS。
- 25 篇核心手册必须从 `docs/README.md` 可达，并分别标出“现行 / 指南 / 事实参考 / 历史资料 / 审计专用”职责。为保留外部深度链接而留下的迁移入口不计入核心篇数，也不得继续复制现行正文。
- 深层页面提供一个自然的下一步，不机械复制整份目录。
- 路径重命名时同一 PR 更新所有入链。
- URL 参数与 settings schema、版本发布与部署分别维护；不要为了减少文件数再次合成难以判断职责的长页面。

## 历史资料

阶段性审计、旧方案和上游比较不删除，先登记到 [历史资料入口](../history/README.md) 或 [Change 注册表](../changes/README.md)，并在顶部增加提示，至少说明：

- 它是哪个时间点或阶段的快照；
- 不代表当前状态；
- 当前入口和事实源在哪里。

不要“修正”历史正文中的当时版本和结论，否则会破坏审计含义。

## 图示和截图

只在关系 materially 更清晰时使用 Mermaid。截图会快速过期、难以本地化，也无法作为可搜索契约；本体系不把截图作为必要步骤。

## PR 检查

纯 Markdown/文档资源变化应只选择 `docs`：

```bash
node scripts/check_markdown_links.mjs
node scripts/scan_repository.mjs
git diff --check
```

普通 GitHub CI 只按需手动运行。若改了模板、MCL、router、代码或依赖，按照本地路径路由运行额外检查是正确行为；不要为了保持 docs-only 拆错文件位置。

## 完成定义

- 正文回答读者任务，不复制 Issue/Plan；
- 当前事实可追溯；
- 旧内容保留或明确迁移；
- 链接与敏感信息检查通过；
- 有 Issue 时回填 PR/Commit、本地验证、按需远端结果、未运行检查和遗留事项；无 Issue 时由直接提交 trailer 与最终交付记录。
